# Развёртывание в существующем проекте

Сценарий: есть 1С-проект, в котором лежит **старая версия системы** (копии
правил, навыков и команд в `.omp/`), и новая машина.

Порядок обязателен: сначала плагины, потом снятие копий. Обратный порядок
оставит проект без правил в моменте.

## 0. Машина

Нужны `git` и `omp`. Доступ к приватным репозиториям — по SSH:

```bash
ssh -T git@github.com     # exit 1 — это нормально, признак успешной аутентификации
```

`config.yml` и `models.yml` в репозитории не входят: в них секреты. На новой
машине их надо завести руками — провайдеры, модели, ключи. Без них сессия не
поднимется, и никакой `sync.sh` этого не исправит.

## 1. Машинный слой

> **Приватный слой.** `sot-omp-core` — личный машинный слой (identity,
> безопасность), доступен не всем. Без доступа к нему этот шаг пропускается:
> плагину `1c` он не нужен, для контура достаточно шагов 2–5 — единственная
> внешняя зависимость, Unica, берётся из публичного
> `IngvarConsulting/unica-marketplace`.

```bash
git clone git@github.com:ntin60775/sot-omp-core.git ~/home/dev/personal/sot-omp-core
cd ~/home/dev/personal/sot-omp-core
./sync.sh          # plan: покажет, что разложится и что лежит лишнего
./sync.sh apply    # разложит в ~/.omp/agent/
```

`[EXTRA]` в выводе — файлы в каталоге агента, которых нет в репозитории. Они не
удаляются: это либо чужие, либо кандидаты на переезд.

## 2. Каталог и плагины

```bash
omp plugin marketplace add IngvarConsulting/unica-marketplace
omp plugin marketplace add ntin60775/sot-omp-marketplace
omp plugin discover sot-omp-marketplace      # что доступно

cd <проект>
omp plugin install --scope project unica@unica
omp plugin install --scope project 1c@sot-omp-marketplace
omp plugin install --scope project ontoship@sot-omp-marketplace   # если нужен KB/dev-flow
```

**Перезапустить сессию.** Навыки подхватит `/reload-plugins`, а MCP-сервер и
хуки — только старт сессии. До перезапуска `unica.*` не существует, и гейты не
работают.

Проверка: `unica.project.status { "cwd": "<корень проекта>" }` → `ready: true`
и список source-set'ов.

## 3. Снять старые копии

**Почему это обязательно.** Проектное правило имеет приоритет 100, плагинное —
90, дедуп по имени файла. Пока копия лежит в проекте, она перекрывает плагинную
целиком: обновления не доезжают, и версия остаётся старой навсегда.

Найти копии — файлы, чьи имена совпадают с плагинными:

```bash
P=.omp/plugins/node_modules/1c-omp
for layer in rules skills commands; do
  [ -d "$P/$layer" ] || continue
  (cd "$P/$layer" && find . -type f) | while read -r f; do
    rel="${f#./}"
    [ -e ".omp/$layer/$rel" ] && echo "копия: .omp/$layer/$rel"
  done
done
```

Найденное — перенести в бэкап внутри проекта, не удалять:

```bash
B=".omp/.backup-$(date +%Y%m%d-%H%M%S)"; mkdir -p "$B"
# затем mv найденных файлов в $B, сохраняя структуру
```

**Что оставить.** Всё, чего нет в плагине: проектные правила и навыки. Их имена
не должны совпадать с плагинными — одноимённый файл заслонит плагинный и
заморозит его. Проектную специфику держать под своим именем: не
`test-contour.md`, а, например, `<проект>-contour.md`.

## 4. Проверка

Сессия в проекте должна:

- видеть навыки `1c-project-bootstrap`, `unica-project-setup`, `unica-test-contour`,
  `1c-mcp-server`;
- показывать в `domain-rules` правила плагина: `1c-bsl-code-style`,
  `platform-tools-stack`, `retry-discipline`, `worktree-env`
  (остальные правила 1С — TTSR: они не листятся, а срабатывают по потоку);
- блокировать правку `src/cf/...` нативным инструментом. Признак того, что
  сработал именно хук, — запись в `~/.omp/logs/rule-audit.jsonl` с
  `"rule":"unica-source-gate"`. Отказ агента без записи в журнале означает, что
  он просто прочитал правило, а хук не загрузился.

## 5. Что остаётся сделать руками

- `v8project.local.yaml` — креды ИБ и путь к платформе; в git не едет.
- `tasks/init-worktree.sh` — обёртка на канон из плагина, см. `rules/worktree-env.md`.
- `.gitignore`: `.omp/plugins/` — машинное состояние, в git ему не место.
- Инфобаза: файловую поднять или скопировать, серверную взять существующую —
  она одна на все деревья проекта.

## Чего не делать

- Не копировать `.omp/` из старого проекта целиком: принесёте ту же старую версию.
- Не снимать копии до установки плагина: проект останется без правил.
- Не править `~/.omp/agent/` руками — следующая раскладка `sync.sh` это затрёт.
- Не ставить 1С-плагины в user scope: контур принадлежит проекту, а ворктри
  наследуют user-scope установку — получите 1С-правила в проектах, где их быть
  не должно.
