# Валидация после создания (причина B постмортема тикета 09)

Остановка на частичных валидациях и заявление о готовности без полного
набора проверок. В тикете 09: готовность заявлена без `cfe.validate` и
`form.validate` — полный набор запущен только после вопроса пользователя
и поймал инлайн-дескрипторы и кривой путь модуля формы, которые сломали
бы загрузку.

## Правило

После ЛЮБОЙ мутации объекта 1С (создание, изменение, удаление) —
прогнать полный валидационный набор для затронутого типа ДО заявления
о готовности:

| Что изменено | Валидация |
|---|---|
| Метаданные (meta.add/edit) | `unica.meta.info` (проверка структуры) |
| Форма (form.compile/edit/add) | `unica.form.validate` |
| Расширение (любое изменение) | `unica.cfe.validate` |
| Конфигурация (cf.edit) | `unica.cf.validate` |
| СКД (dcs.compile/edit) | `unica.dcs.validate` |
| Макет (mxl.compile) | `unica.mxl.validate` |
| Роль (role.compile/edit) | `unica.role.validate` |
| Подсистема (subsystem.compile/edit) | `unica.subsystem.validate` |
| Интерфейс (interface.edit) | `unica.interface.validate` |
| BSL-код (code.patch) | `unica.code.diagnostics` + guard-скрипт стиля |

## Порядок

1. Мутация (например `unica.meta.add`).
2. Валидация затронутого типа (например `unica.cfe.validate` если в
   расширении).
3. Валидация формы, если создавалась/менялась форма.
4. `unica.code.diagnostics` по изменённым модулям.
5. Только после зелёной валидации — заявление о готовности.

## MUST NOT

- Заявлять готовность без полного валидационного набора.
- Останавливаться на частичной валидации (например только `meta.info`
  без `cfe.validate`).
- Пропускать `form.validate` при создании формы.
- Ждать вопроса пользователя для запуска полного набора.
