# Ворктри: воркспейс, база и тестовое окружение

При создании ворктри агент НЕ инициализирует воркспейс Unica и не копирует
тестовое окружение. В ворктри после `git worktree add` есть только то, что в
git: `v8project.yaml`, `tools/VAParams.template.json`. Всё остальное (креды,
рабочий профиль Vanessa, инструменты тестов, инкрементальное состояние, база)
— в gitignore и отсутствует.

## Что отсутствует в свежем ворктри

| Что | Зачем нужно |
|---|---|
| `v8project.local.yaml` | креды ИБ, путь и версия платформы |
| `tools/VAParams.json` | профиль Vanessa-прогона; без него `v8-runner` падает на валидации конфига при ЛЮБОЙ операции. Собирается из шаблона, не копируется: в нём абсолютный `ПутьКИнфобазе` |
| `tools/va-env.local.json` | креды тест-клиента для шагов Vanessa, подключающих клиент сами |
| `build/tools/` | `YAxUnit-*.cfe`, `vanessa-automation-single.epf` — артефакты тестов |
| `build/hash-storages/` | инкрементальное состояние сборки (без него первая сборка полная) |
| **инфобаза** | **файловая — своя у каждого дерева; серверная — ОДНА на все** |

## Профиль Vanessa собирается, а не копируется

`tools/VAParams.json` содержит **абсолютный** `ПутьКИнфобазе`. Скопировать его
из основного дерева — значит запустить тесты на базе основного дерева: прогоны
зелёные, расширение собрано, а сценарии идут на старом состоянии. Замок
`unica-gate` этого не ловит — он смотрит строку подключения воркспейса, а
тест-клиент ходит по пути из `VAParams.json`.

Поэтому инициализатор не копирует этот файл, а собирает его из
`tools/VAParams.template.json` и `v8project.local.yaml` для **этого** дерева
(там же создается `tools/va-env.local.json`, креды обоих — только локально):

```bash
python3 .omp/plugins/node_modules/1c-omp/skills/1c-project-bootstrap/scripts/bootstrap-local-config.py --tree <ворктри>
```

Проверка, что прогон шёл по базе ворктри: `ls -lt <ворктри>/build/ib/1Cv8Log/*.lgp`
— mtime журнала обновляется прогоном. В проектах со старым каноном, который
всё же скопировал файл, путь переписывают вручную и проверяют тем же журналом.

## Правило: один скрипт

После `git worktree add` — ОБЯЗАТЕЛЬНО запустить инициализатор. Канон живёт в
плагине `1c`:

```bash
.omp/plugins/node_modules/1c-omp/skills/1c-project-bootstrap/scripts/init-worktree.sh <ворктри>
.omp/plugins/node_modules/1c-omp/skills/1c-project-bootstrap/scripts/init-worktree.sh <ворктри> --empty-ib
```

В проекте есть обёртка `tasks/init-worktree.sh`, которая зовёт канон — правки
вносить в плагин, не в обёртку.

Скрипт копирует из основного дерева `v8project.local.yaml`, `build/tools/`,
`build/hash-storages/`, собирает профиль Vanessa под это дерево, ставит плагины
проекта, разбирается с базой и проверяет результат. Только реальные копии,
НЕ симлинки.

## Шаг плагинов убивает живой MCP-сервер Unica

Шаг 6 инициализатора выполняет `omp plugin install --scope project` —
переустановка **пересоздаёт** каталог кэша плагина
`~/.omp/plugins/cache/plugins/unica___unica___<ver>`, а у давно живущего
stdio-процесса MCP-сервера рабочий каталог остался на удалённом иноде.

Симптом: **каждый** вызов `mcp__unica__*` падает сразу и без ретраев,
независимо от `cwd` в аргументах:

```
MCP error -32000: failed to read current directory: No such file or directory (os error 2)
retryable: no
```

Диагностика и восстановление — правило `unica-mcp`. Принципиально здесь другое:

- вызывать инициализатор **до** первых `unica.*`-вызовов в сеансе;
- если сеанс уже работает, шаг плагинов ломает его штатно, а не по ошибке
  оператора: на это время либо пропустить шаг плагинов (копирование без
  переустановки), либо сразу выполнить восстановление для зависших сессий;
- чужие сессии не трогать: убивает их сеанс/оператор, находку доложить.

## Работа в ворктри: только абсолютные пути

Инструменты агента (`read`/`edit`/`write`, `glob`/`grep` без явного `path`)
резолвят относительные пути от **cwd сессии** — а сессия живёт в основном
дереве. Правка `docs/foo.md` «в ворктри» уходит в основное дерево: изменения
видны в `git status` основного дерева, а в ворктри их нет.

- правки внутри ворктри — абсолютным путём либо через `bash` с `cd` в ворктри;
- git — `git -C <ворктри> …`, не полагаясь на текущий каталог;
- после правок сверить оба дерева: в ворктри изменения есть, основное — чистое;
- если изменения уже уехали: перенести в ворктри и восстановить основное
  (`git -C <основное> checkout -- <файлы>`).

## База: изоляции у серверной не бывает

**Файловая** (`File=build/ib`, путь относительный) — у каждого дерева своя.
Если её нет, скрипт копирует базу из основного дерева; с `--empty-ib` создаёт
пустую. Пустая годится для сборки из исходников и тестов без данных; для
Vanessa и BDD нужна полная.

**Серверная** (`Srvr="…";Ref="…"`) — **одна на все деревья проекта**. Отдельную
серверную базу на каждый ворктри не поднять: размер и кластер. Значит изоляции
здесь нет и быть не может, а достижимый инвариант другой:

> **В один момент с серверной базой работает одно дерево.**

Держит его замок хука `unica-gate`: операция, меняющая базу (`build`, `load`,
`update`, `test`, `launch`, `make`), берёт замок по строке подключения; другое
дерево получит отказ с указанием держателя. Замок снимается по завершении
операции, а долгие задачи держат его до конца. Умерший процесс замок не
удерживает — он перехватывается.

Для файловых баз ключ замка разный у каждого дерева, поэтому замок там не
мешает вообще.

`build/hash-storages/` копируется только когда состояние базы совпадает с
основным деревом: для серверной базы и для скопированной файловой — да, для
пустой — нет, иначе инкрементальная сборка пойдёт по чужому состоянию.

## Проверка после инициализации

```json
unica.project.status { "cwd": "<корень ворктри>" }
```

Ожидание: `ready: true` + список source-set'ов. Все последующие вызовы Unica —
с `cwd` корня ворктри, не основного дерева.

## Если артефактов нет в основном дереве

`build/tools/` отсутствует → в основном дереве:

```json
unica.runtime.execute { "cwd": "<main>", "operation": "tools-download",
                        "tool": "vanessa", "dryRun": false }
unica.runtime.execute { "cwd": "<main>", "operation": "tools-download",
                        "tool": "yaxunit", "dryRun": false }
```

Затем повторить инициализатор.

## Снятие ворктри

Ворктри короткоживущий: после merge ветки его снимают, иначе копии базы копятся
(копия файловой ИБ — десятки гигабайт на дерево). Порядок обязателен: обратный
даёт симптом «каталог вернулся через минуту».

1. **Остановить сервисы Unica по этому пути** — только по конкретным PID:

   ```bash
   pgrep -af "<ворктри>"     # unica --workspace-service …, bsl-analyzer mcp serve …
   kill -TERM <PID> …
   ```

   MCP-вызовы Unica поднимают для воркспейса фоновые сервисы, которые переживают
   `git worktree remove` (осиротевшие процессы с `ppid=1`, `--idle-secs 7200`) и
   пересоздают каталог ворктри со своим `.build/unica/…`.
2. **Снять ворктри** из основного дерева: `git worktree remove --force <ворктри>`.
   `--force` обязателен: в ворктри лежат игнорируемые `build/`, `.build/`, `.omp/`.
3. **Удалить ветку** — только после шага 2, иначе ветка занята ворктри:
   `git branch -d <ветка>`. Именно `-d`: откажет, если ветка не влита, — это и есть
   проверка, что работа не потеряна.
4. **Почистить служебные записи:** `git worktree prune`.
5. **Проверить:** `ls -d <ворктри>` → «No such file or directory»;
   `git worktree list` → только основное дерево; `git branch` → без ветки задачи;
   повторный `ls -d` через ~30 с — каталог не должен вернуться.

Снятие разрушительно (десятки гигабайт) — выполняется по явной команде человека,
а не по инициативе агента.

## MUST NOT

- Создавать ворктри без запуска инициализатора.
- Копировать `tools/VAParams.json` из основного дерева — в нём абсолютный путь
  к чужой базе; только сборка из шаблона под своё дерево.
- Править файлы ворктри относительными путями: они уходят в основное дерево —
  только абсолютные пути или `bash` с `cd`.
- Запускать шаг плагинов, пока сеанс держит живой Unica MCP: переустановка
  ломает его (см. раздел «Шаг плагинов…»), и восстановление — уже ручная работа.
- Использовать симлинки на `build/tools`, `VAParams.json` в ворктри
  контейнера — только реальные копии (distrobox не видит симлинки).
- Считать ворктри изолированным, если база серверная: она общая.
- Грузить и тестировать в серверную базу из двух деревьев одновременно —
  замок это ловит, но обходить его нечем.
- Вызывать Unica с `cwd` основного дерева, работая в ворктри.
- Запускать сборку или тесты в ворктри без проверки `unica.project.status`.
- Повторять идентичные упавшие прогоны (3+ раза) без диагностики.
- Снимать ворктри, не остановив сервисы Unica: они вернут каталог; удалять ветку
  до снятия ворктри; снимать ворктри с незакоммиченными правками.

## Детерминированный слой

Хук `unica-gate.ts`:
- блокирует вызовы Unica из ворктри, если в нём нет `v8project.local.yaml` или
  `build/tools/`;
- блокирует операции с базой, если её держит другое дерево.
