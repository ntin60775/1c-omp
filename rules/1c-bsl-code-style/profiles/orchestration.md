# Профиль: orchestration-код

Этот файл — project-specific profile. Подключайте его только если модуль
действительно является orchestration-модулем по признакам ниже.

## Когда считать модуль orchestration-модулем

Если модуль:

- координирует несколько этапов;
- вызывает соседние модули;
- собирает контекст выполнения;
- пишет журнал, прогресс или telemetry;
- сам почти не содержит предметных вычислений,

то это orchestration-модуль.

Если модуль не удовлетворяет этим признакам, не навязывайте ему orchestration-
playbook только потому, что такой шаблон хорошо работает в интеграционном коде.

## Правила для orchestration-модуля

1. Во внешнем интерфейсе оставляйте только use-case методы.
2. Внутри разделяйте шаги сценария на предметные блоки:
   - сбор контекста;
   - выполнение этапов;
   - журналирование;
   - инфраструктурные вызовы.
3. Читайте код сверху вниз как сценарий.
4. Каждому шагу сценария дайте отдельное, но короткое имя.
5. Не тащите в orchestration-модуль повторную доменную подготовку данных, если она уже живет в соседнем слое.
6. Если сценарий ветвится по набору флагов, сначала считайте флаги в локальные булевы переменные, потом стройте ветки выполнения.
7. Если orchestration-модуль управляет подготовкой пакетов обмена, его соседние
   шаги должны выглядеть как семейство однотипных use-case методов, а не как
   смесь монолита и локальных импровизаций.

## Хорошая форма orchestration-кода

Часто orchestration-сценарий читается как последовательность коротких шагов:

- вход в сценарий;
- сбор или подготовка контекста;
- выполнение этапов;
- завершение и фиксация результата.

Это пример ритма сценария, а не словарь обязательных имен.

## Последовательность стадий для методов подготовки этапа

Если orchestration-метод собирает данные для отдельного контейнера результата,
его полезно читать как короткий сценарий из повторяемых стадий.

Типовой порядок для такого метода:

1. Сбор исходных данных и запуск подготовительных шагов.
2. Вычисление локальных пакетов из уже собранных данных.
3. Создание контейнера результата.
4. Заполнение `РезультатЭтапа.Пакеты`.
5. Заполнение `РезультатЭтапа.КонтекстЭтапа`.
6. Присвоение результата в `ВозвращаемоеЗначение` и финальный
   `Возврат ВозвращаемоеЗначение`.

Это не догма для любого BSL-метода, но хороший базовый шаблон для модулей
подготовки пакетов обмена, где соседние `Этап...` должны читаться по
предсказуемому ритму.

## Смысловые пустые строки между стадиями

В orchestration-методе пустая строка может разделять не только блоки табов, но
и смысловые стадии сценария.

Уместно отделять одной пустой строкой:

- блок `Подготовка...` шагов от блока вычисления локальных пакетов;
- блок вычисления локальных пакетов от строки
  `РезультатЭтапа = НовыйРезультатЭтапа();`;
- создание `РезультатЭтапа` от последующего заполнения `Пакеты`;
- заполнение `Пакеты` от заполнения `КонтекстЭтапа`;
- заполнение `КонтекстЭтапа` от `Возврат`.

Такие разрывы полезны, если они помогают видеть метод как последовательность
стадий сверху вниз. Они не должны превращаться в декоративные пустые строки
после каждой отдельной строки.

## Как трактовать `НовыйРезультатЭтапа`

Строка
`РезультатЭтапа = НовыйРезультатЭтапа();`
в orchestration-методе такого типа — это отдельная точка перехода:

- всё выше подготавливает данные этапа;
- всё ниже заполняет уже созданный контейнер результата.

Поэтому сразу после неё допустима и часто полезна пустая строка, если дальше
идёт серия `РезультатЭтапа.Пакеты.Вставить(...)`.

Точно так же полезна пустая строка между последним `Пакеты.Вставить(...)` и
первым `КонтекстЭтапа.Вставить(...)`, потому что это переход между двумя
разными слоями результата.

## Граница применения

- Эти правила относятся к orchestration-методам подготовки этапов и пакетов.
- Не нужно переносить их автоматически в короткие service-функции и обычные
  helper-методы.
- Если в методе нет явных стадий, пустые строки не нужно добавлять
  искусственно только ради симметрии.

## Что не нужно делать

- не дублировать слой подготовки данных;
- не вводить повторную нормализацию уже готового DTO без доказанной необходимости;
- не плодить вспомогательные методы-доступоры только ради доступа к полю контекста;
- не экспортировать внутренние шаги orchestration-сценария.
- не разбрасывать string-literal имена флагов по всему методу, если их можно локализовать в одном верхнем блоке.
- не пытаться заменить семейство предметных шагов одним универсальным
  вспомогательным методом сборки пакетов без доказанной общей инвариантной логики.
