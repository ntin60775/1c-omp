# Именование

## Базовые принципы

1. Имена процедур, функций и параметров берите от терминов предметной области.
   Из имени должно быть понятно назначение.
2. Хорошо выбранное имя процедуры, функции и параметров объясняет смысл
   лучше, чем комментарий. Если имя подобрать трудно, это может быть сигналом
   проблемы в декомпозиции или архитектуре.
3. Не используйте в имени лишние технические подробности, если они не помогают
   понять смысл.
4. Не называйте методы и переменные по сырым ключам внешнего контракта, если
   это не часть устойчивого интеграционного словаря модуля или буквальный
   литерал внешнего обмена.
5. Для семейства однотипных вспомогательных методов используйте единый шаблон
   именования, а не набор случайных синонимов.

## Граница со standards-review

- Этот reference удерживает только базовые naming-принципы читаемости.
- Частные правила `#std647` про глагольную форму процедуры, имя функции от
  возвращаемого значения, `Новый...`, `Это...` и исключения `6.4` / `6.5`
  принадлежат навыку `$1c-bsl-review-standards`.
- Поэтому текущий skill не вводит собственных жестких запретов на отдельные
  глаголы вроде `Получить`, `Сохранить`, `Сбросить`. Такие формы могут быть
  сигналом перепроверить имя по `#std647`, но не считаются автономным
  style-нарушением без обращения к стандарту.
- Если локальная эвристика этого skill-а расходится с `v8std`, источником
  истины считаются стандарты.

## Что считать удачным локальным именованием

Интеграционные имена и примеры ниже — это не обязательный шаблон для любого
модуля. Они показывают локальную форму на типичном для проекта классе задач.

Предпочтительно использовать предметные имена:

- `КонтекстВыгрузки()`
- `ПакетыКонтрагентовДляОтправки()`
- `ДетализацияФлаговВыгрузки()`
- `НормализованноеНаименованиеОрганизации()`
- `ТекстСообщения`
- `ВнешнийИдентификатор`
- `ДоговорКонтрагента`

Избегать технического шума и случайных имен:

- `Результат1`
- `Значение2`
- `Данные`
- `СтруктураСтроки`, если это не реально устоявшийся термин в текущем модуле
- `Преф_ТекстЗапросаПодготовкаСклады()`, если префикс не нужен внешнему контракту
- случайную смесь синонимов внутри одного семейства helper-ов

Для детальной локальной формы query-helper-ов и orchestration-семейств
используйте project-specific профили:

- `../profiles/query-texts.md`
- `../profiles/orchestration.md`

## Интеграционный словарь и гибридные идентификаторы

На границе интеграции допустимы гибридные имена, если они выражают устойчивый
внешний термин и реально помогают сопоставить код с контрактом:

- `EndpointId`
- `UserIdMozen`
- `GUIDПлатежа`
- `ИдентификаторОперацииMozen`
- `РезультатAPI`

Плохой признак не сам английский фрагмент, а механическое копирование сырого
ключа без осмысленной локальной роли.

## Для переменных

1. Имя переменной должно описывать роль значения в текущем месте кода.
2. Если значение меняет представление, называйте старое и новое состояние по-разному.
3. Если переменная хранит отдельный собранный объект, называйте ее по сущности объекта, а не по операции добавления, передачи или присваивания.
4. Не используйте переменные-обертки без прироста смысла.
5. Если значение проходит несколько семантических стадий, называйте каждую стадию отдельно: внешний идентификатор, ссылка, данные ссылки, итоговое доменное значение.
6. Даже если внешний контракт использует англоязычные ключи, локальные
   переменные по возможности называйте по-русски и по смыслу. Но устойчивые
   интеграционные идентификаторы и vendor-термины допустимы, если иначе
   теряется связь с внешним контрактом.

Предпочтительно:

- `ТекстСообщения`
- `ДетализацияФлагов`
- `КороткоеИмяФлага`
- `ШиротаСтрокой`
- `ПараметрВыбораТипСклада`
- `ОписаниеОповещенияЗакрытия`
- `ВнешнийИдентификатор`
- `КлючАналитикиПоПартнерам`
- `ДанныеКлюча`
- `ДоговорКонтрагента`

Избегать:

- `Результат1`
- `Значение2`
- `Данные`
- `СтруктураСтроки`, если это не реально устоявшийся термин в текущем модуле

Даже в коде адаптации внешнего контракта и в модулях подготовки пакетов обмена
предпочтительно:

- `ВнешнийИдентификатор`
- `Наименование`
- `Склады`
- `ВидыЦен`

Англоязычные фрагменты допустимы не только внутри строковых литералов внешнего
контракта, но и в устойчивом интеграционном словаре модуля, если они помогают
точно связать локальное имя с внешним API или vendor-термином.

## Legacy-префиксы во внутренних методах

При рефакторинге существующего кода не переносите во внутренние вспомогательные
методы исторические префиксы вроде `Преф_`, если они:

- не являются частью внешнего контракта;
- не нужны для различения с соседним публичным API;
- не помогают читателю понять роль метода.

Если вспомогательный метод стал обычной внутренней функцией модуля, предпочтительно дать ему
обычное предметное имя без исторического префикса.

## Для областей

Используйте области как разделы ответственности:

- `ПрограммныйИнтерфейс`
- `СлужебныеПроцедурыИФункции`
- `ОркестрацияСценария`
- `АдаптацияКонтракта`
- `Инфраструктура`
- `Журналирование`

Не вводите область только ради количества. Область должна отражать роль кода.
