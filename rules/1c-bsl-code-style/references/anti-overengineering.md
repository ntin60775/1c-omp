# Как не переусложнять код

## Главное правило

Не добавляйте абстракцию, защиту или нормализацию, если у нее нет подтвержденной
причины в текущем сценарии.

Это правило работает и в обратную сторону: не удаляйте промежуточные шаги только
потому, что код можно записать короче. Если шаг отражает отдельную семантическую
стадию данных, его сохранение не является оверинжинирингом.

## Когда вспомогательный метод не нужен

Вспомогательный метод не нужен, если он:

- просто оборачивает один вызов;
- не скрывает нестабильный контракт;
- не упрощает чтение внешнего метода;
- не выделяет отдельную ответственность.

## Когда нормализация не нужна

Не добавляйте вспомогательный метод нормализации, если:

- данные приходят из уже контролируемого слоя;
- тип и форма значения гарантированы соседним модулем;
- код не показывает реального сценария пустого или ошибочного значения;
- это превращает простой поток данных в цепочку страховочных оберток.

## Когда защитный код оправдан

Защитный код оправдан, если:

- модуль действительно стоит на границе с недоверенным источником;
- есть подтвержденный альтернативный сценарий вызова;
- без него возможен реальный сбой на существующих данных;
- пользователь явно зафиксировал, что контракт входа не гарантирован.

## Практические эвристики

1. Если метод по имени выглядит как защитная, нормализующая или техническая обертка над уже гарантированными данными, проверьте, не скрывает ли он просто прямой доступ к ним.
2. Если после удаления вспомогательного метода код становится короче и не теряет ясности, этот метод лишний.
3. Если каждая вторая строка модуля занимается приведением “на всякий случай”, скорее всего модуль уже делает работу не своего слоя.
4. Если переменная фиксирует переход `внешний идентификатор -> внутренняя ссылка -> данные -> бизнес-значение`, это обычно полезная форма кода, а не шум.
5. Если переменная хранит отдельно собранный прикладной объект вроде `ПараметрВыбора` или `ОписаниеОповещения`, это тоже обычно полезная форма кода, а не шум, даже при одной точке использования.
6. Если отдельная переменная дает удобную точку останова и возможность тестовой подмены значения, это практическая польза, а не стилистическое украшение.

## DRY против стабильной формы в интеграционных модулях

В больших модулях подготовки обмена не пытайтесь любой ценой убрать повторяемую
форму кода.

Если десять методов читаются по одному понятному шаблону, это часто лучше, чем:

- один “универсальный” вспомогательный метод на все случаи;
- общий builder с десятком callback-ов;
- скрытая магия ради сокращения числа строк.

Повторяемая форма допустима, если она:

- делает соседние методы предсказуемыми;
- упрощает навигацию по модулю;
- снижает риск ошибиться в преобразованиях на границе внешнего контракта.

## Когда одноразовый вспомогательный метод все-таки нужен

В большом унаследованном модуле вспомогательный метод с одной точкой вызова может быть оправдан, если
он:

- выносит длинный query-text;
- изолирует извлечение из вложенной коллекции;
- оформляет отдельную нормализацию;
- делает соседние методы структурно похожими и тем самым упрощает модуль в
  целом.

Ориентир простой: если после выделения вспомогательного метода читать модуль сверху вниз стало
легче, а не сложнее, это не оверинжиниринг.

Тот же критерий применяйте к промежуточным переменным:

- предметный объект сценария можно и нужно называть отдельно;
- наблюдаемую в отладке промежуточную стадию тоже можно и нужно сохранять отдельно;
- техническую оболочку без собственной роли отдельно называть не нужно;
- лишней считается не "одноразовая" переменная сама по себе, а переменная,
  которая ничего не объясняет.
