# Инфобаза: ibcmd и конфигуратор

Прямые операции с ИБ — когда Unica их не покрывает (первичная установка `.cfe`,
контур из исходников, дамп без MCP-маршрута, снятие поддержки, журналы).
Каждый пункт здесь стоил времени на проектах; «правильный» путь перечислен первым.

## Выбор инструмента

| Задача | Файловая ИБ | Серверная (кластерная) |
|---|---|---|
| загрузить `.cfe` расширением | `ibcmd infobase config load --db-path … --extension=<Имя>` | конфигуратор `1cv8 DESIGNER /S … /LoadCfg … -Extension <Имя>` |
| снять/включить safe mode | `ibcmd extension update --name=<Имя> --safe-mode=no` | только руками оператора в конфигураторе |
| снять/вернуть признак главного узла РИБ | BSL `ПланыОбмена.УстановитьГлавныйУзел(…)` | там же |
| полная загрузка большой конфигурации | конфигуратор (см. лимит ниже) | конфигуратор; `ibcmd` требует `infobase.dbms` |
| журнала регистрации | `ibcmd eventlog export --format=json --out=… <база>/1Cv8Log` | то же, путь к `1Cv8Log` |

**`ibcmd` с кластерными ИБ не работает**: `--server` не распознаётся, а на
серверной ИБ операции падают с «validation error: server-based IBCMD connection
requires infobase.dbms.kind».

**`ibcmd` не загружает большую конфигурацию в файловую ИБ**: его `ConfigSave`
пишет один внутренний файл, а у крупных ERP он превышает лимит файловой ИБ
(4 ГБ на внутренний файл) → exit 255 «Превышен максимально допустимый размер
внутреннего файла … 1Cv8.1CD». Лечится `builder: DESIGNER`; `ibcmd` остаётся
для административных операций.

## Креды и пути

- **`--user` / `--password` — в КОНЕЦ команды.** Аргумент, стоящий раньше
  позиционных, разбирается с ошибкой («Ошибка разбора параметра»).
- **Промпт `Пароль для '<пользователь>':` означает неверный пароль**, а не
  «пароль не передан»: с верным паролем команда идёт молча.
- **`ibcmd extension list` без учётки уходит в ожидание пароля и висит** — в
  фон такой запуск не отправлять.
- **Относительный `--db-path` опасен**: на части операций он разрешается не от
  текущего каталога, а от каталога данных автономного сервера — база создаётся
  не там, где ждёшь, а следующие `ibcmd`-команды по тому же пути работают с
  **другой** базой, чем клиент и конфигуратор. Спасает только абсолютный путь.
- **`--apply` без `--force` завершается не применив БД**: на вопрос «Принять
  изменения и продолжить обновление [y/n]» без stdin ответа нет. Либо `--force`,
  либо отдельный шаг `ibcmd infobase config apply --db-path=<абс> --force`.
- **Креды ИБ — в `v8project.local.yaml`**, читаются скрипт-обёрткой; в чат, лог
  и аргументы командной строки пароль не выводить. Unica и v8-runner читают
  оверлей сами, поэтому в их командах пароль не нужен.

## Пустая ИБ и пользователи

- Файловая ИБ **без пользователей** пускает без `/U /P`; как только пользователь
  создан, везде нужна учётка. Передача пустого пароля через `P ""` даёт
  «Пользователь ИБ не идентифицирован» — лучше `/P` не передавать вовсе.
- **ИБ, собранная из исходников, пользователей не содержит вовсе**: если
  креды остались в оверлее, загрузка падает тем же «Пользователь ИБ не
  идентифицирован» — на таком контуре креды из оверлея убирают.

## Монополия: кто держит базу

- **Конфигуратор держит монопольную блокировку** на всё время работы: сборку
  и загрузку при открытом конфигураторе не запускать; зависший
  `1cv8 DESIGNER` — `ps aux | grep 1cv8`.
- **Блокировка может быть удалённой**: падение с exit 4 «С этой информационной
  базой уже работает конфигуратор: компьютер: …, сеанс: N» при пустом локальном
  `pgrep` — это чужой сеанс. Не искать локальные процессы: просить оператора
  закрыть его.
- **Клиент переживает закрытие формы**: процесс `1cv8` остаётся живым и держит
  базу. Следующий `config apply` падает «Ошибка исключительной блокировки
  информационной базы» (и корректно откатывается). После каждого ручного
  прогона процесс снимать.
- **Опубликованная база отпускает файл только формально**: веб-сервер держит
  дескрипторы `1Cv8.1CD` между запросами, поэтому **из HTTP-сеанса (в том числе
  через расширение `MCP_Сервер`) монопольный режим недостижим в принципе** —
  `УстановитьГлавныйУзел` вернёт «Ошибка разделения доступа к базе данных».
  Монопольные операции делать клиентским сеансом с остановленной публикацией.
- **Зависший `ibcmd` держит базу, хотя его «отменили»**: отмена фонового задания
  снимает только обёртку (`distrobox`/`bash`), внутренний процесс жив. Искать по
  дескрипторам (`ls -l /proc/<pid>/fd` — там путь к базе), снимать по
  конкретному PID.

## Копия базы ≠ бэкап

`cp -a` базы, снятой **до того, как платформа хоть раз открыла базу**, не
аутентифицирует («Пользователь ИБ не идентифицирован»). Годная копия — та, что
снята после первого открытия. Проверять копию нужно сразу, а не в момент, когда
она понадобится для отката.

Платформа при этом **тихо создаёт файловую базу на несуществующем пути**, если
открыть такой путь: в каталоге оказываются одни lock-файлы, а каталог выглядит
как настоящая база.

## Проверка результата

- **Конфигурация сравнивается по объектам, а не по байтам.** Повторно
  сохранённый `.cf`/`.cfe` отличается от исходного размером и содержимым,
  оставаясь той же конфигурацией. Сверка — выгрузкой информации о конфигурации:

  ```bash
  ibcmd infobase --db-path=<база> config export info --out=<каталог> --user … --password …
  cmp <каталог>/ConfigDumpInfo.xml <эталон>/ConfigDumpInfo.xml
  ```

  То же для расширения: `config export info --extension <Имя>`. Совпадение
  `ConfigDumpInfo.xml` означает совпадение состава объектов.
- **Состав расширений** — `ibcmd infobase config extension list --user … --password …`.
- **Ошибки применения расширений** в журнале — события
  `_$Session$_.ConfigExtensionApplyError`.

## Дамп

- **Полной выгрузки через MCP нет**: `unica.runtime.job.start` отказывает
  («asynchronous applied full dump is not supported»), а синхронные
  `unica.runtime.execute` режутся 30-с лимитом — процесс отрабатывает, а
  публикация оборвана, дерево не меняется и staged-каталог выбрасывается.
  В таком случае выгрузку запускает встроенный раннер напрямую (обход
  допустим: названной возможности в контракте нет).
- **Выгрузка удаляет всё, что не принадлежит конфигурации** (например
  `AGENTS.md` в целевом каталоге) — после неё вернуть наши файлы из git.
- **Перед загрузкой** убедиться, что `src/cf` не старше конфигурации базы
  (`v8-runner dump --mode full`): иначе загрузка откатит базу на состояние
  исходников.

## Снятие с поддержки

`ibcmd … config support disable --force` — это **полное** снятие с поддержки,
а не «разрешить изменение с сохранением поддержки»: конфигурация теряет связь
с поставщиком, обновления через `.cfu` больше не встают, обратно одной командой
не возвращается. Рычаг «сохранить поддержку» есть только в конфигураторе
(«Поддержка → Настройка поддержки»). Выбор между путями — решение оператора.

## Программного удаления расширения нет

`РасширенияКонфигурации` в коде умеет `Получить()` и фоновые задания, но не
`Удалить()`; `ibcmd extension delete` требует учётку ИБ, а режим `extension`
учётку не принимает. Удаление — только конфигуратор
(«Конфигурация → Расширения конфигурации → Удалить»).

## Тонкий клиент игнорирует `/Execute`

`1cv8c ENTERPRISE … /Execute <epf>` открывает базу и молча ничего не делает:
ни окна, ни диалога, ни ошибки. Тот же файл и тот же ключ в толстом клиенте
(`1cv8`) исполняются. Если обработка «не открылась» — сначала проверить
клиент, а не обработку.

## MUST NOT

- Передавать пароль в командной строке, не попросив скрипт-обёртку (он виден в
  `ps`); передавать пустой `P ""`.
- Оставлять относительный `--db-path` в цепочках команд.
- Запускать сборку/загрузку при открытом конфигураторе или из HTTP-сеанса
  с требованиями монополии.
- Считать `cp -a` каталога базы бэкапом.
- Сравнивать `.cf`/`.cfe` побайтово как доказательство эквивалентности.
