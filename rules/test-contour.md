# Тестовый контур 1С: рабочие команды и грабли


## Прогон тестов: только встроенный раннер Unica

Единственный раннер — **v8-runner, встроенный в Unica** (в Unica 0.12.3 — v8-runner 0.5.1).
Путь версионирован — резолвить динамически, не хардкодить:

    V8R=$(ls -d ~/.codex/unica/runtimes/*/linux-x64/bin/linux-x64/v8-runner 2>/dev/null | sort -V | tail -1)

Контрактный gap (проверено 2026-08-28): `unica.runtime.execute operation: test`
НЕ экспонирует флаг `--no-build` и всегда пересобирает ВСЕ source-set'ы, включая
основную конфигурацию, — десятки минут, неприемлемо.

**Инвариант пересборки: расширение грузится ВСЕГДА полной пересборкой; основная
конфигурация НЕ пересобирается никогда.** Partial load расширения не экономит: он
падает на формах (см. грабли ниже), а MCP всё равно ретраит полной пересборкой —
платишь дважды. Полная загрузка расширения ~2–3 мин, это дешевле любой возни с
partial-сбоем. Основная конфигурация живёт в ИБ как есть: её изменения загружает
оператор, раннер запускается с `--no-build`.

Штатный цикл (одинаков для YAxUnit и Vanessa):

1. Загрузка изменений — через MCP, по source-set'у:
   `unica.runtime.execute` `operation: build`, `sourceSet: "<имя source-set'а>"`
   (каждое изменённое расширение отдельно, включая тестовое). Полная загрузка
   расширения ~2–3 мин.
2. Прогон — прямой запуск встроенного раннера с `--no-build` (обход MCP-контракта,
   флаг там отсутствует), под собственным дисплеем:
   ```bash
   P1C=.omp/plugins/node_modules/1c-omp

   # все тесты: приёмка и регресс; артефакты в build/out/yaxunit/, вердикт сам
   "$P1C/skills/unica-test-contour/scripts/test-yaxunit.sh"

   # отладка одного набора — прогон по модулю: фикстуры соседних не тянет,
   # картина падений чище
   "$P1C/skills/unica-test-contour/scripts/test-yaxunit.sh" --module <ИмяМодуля>

   # Vanessa (профиль из v8project.yaml)
   "$P1C/skills/unica-test-contour/scripts/xvfb-run-1c.sh" -- "$V8R" test va --no-build
   ```
   Запуск из корня worktree/проекта. Обёртки сами выбирают дисплей (свой
   виртуальный, номер выдаёт `Xvfb -displayfd`) — фиксированный `:99` не
   нужен, параллельные прогоны друг другу не мешают.

Легитимность обхода: правила проекта имеют приоритет над инструкциями skill'а
Unica («Do not start internal runner… directly»); обход допустим как единственный
путь к `--no-build` и/или по явной команде оператора. Перед обходом называть
отсутствующую возможность контракта.

builder: **DESIGNER**: на серверной ИБ IBCMD требует прямого доступа к СУБД
(`infobase.dbms`), а в файловую крупную конфигурацию `ibcmd` не грузит вообще —
подробности и другие расхождения `ibcmd`/конфигуратора в `rule://ib-contour`.

## Грабли прогона (проверено 2026-08-28, дополнено 2026-09-01)

- `--feature` у `"$V8R" test va` матчится **относительно `КаталогФич`**: передавать
  только имя файла (`"ИмяФичи.feature"`), а не путь `"features/ИмяФичи.feature"`.
  Иначе — «Сценарии для выполнения не обнаружены», пустой junit, exit с
  `junit file is empty` при живой ИБ и корректных тегах.
- `unica.runtime.job.wait` обрезается хостовым 30-с лимитом MCP — не полагаться
  на него: опрашивать `unica.runtime.job.status` (обязательно с `cwd` воркспейса,
  иначе «record is missing») или ждать паузой вне MCP.
- `unica.runtime.job.start` `operation: build` при провале partial load
  **сам ретраит одной полной пересборкой** (`--full-rebuild`); итог — exit 0,
  в warnings: «reported a completed partial load failure; Unica retried once».
  Повторный manual full-rebuild не нужен.
- Partial load расширения падает с «Исключение XDTO произошло при чтении
  файла- …Form.xml», когда в partial-списке есть **формы** (проверено
  2026-09-01: падает на любой версии формы, full load той же версии проходит).
  Модули (.bsl) partial-ом грузятся, но исключения ради них не делаем — см.
  инвариант выше: расширение всегда полной пересборкой
  (`"$V8R" build --source-set <имя> --full-rebuild` или MCP
  `unica.runtime.execute build` по source-set'у). Full rebuild нужен и после
  пересоздания объекта в конфигураторе: у него новый UUID, partial по старому
  не сойдётся. Основную конфигурацию по-прежнему не пересобирать.
- **Прогон по несуществующему модулю виснет до таймаута**: YAxUnit уходит в
  «Зацикливание обработки глобальной ошибки» («Задано неправильное имя атрибута
  структуры», 100 повторов), клиент остаётся открытым, раннер ждёт его
  завершения. Проверять имя модуля до запуска; при зависании — стоп-протокол
  (кадр дисплея → убить клиента по PID → удалить `run.inprogress`).
- **Конфигуратор может держать блокировку извне**: сборка падает с exit 4
  «С этой информационной базой уже работает конфигуратор: компьютер: …, сеанс: N»,
  а локальный `ps aux | grep 1cv8` пуст — блокировка удалённой сессии. Не искать
  локальные процессы: просить оператора закрыть тот сеанс.

## Регресс собственного фикса и порядок операций (факапы A3, D1 тикета 10)

- **Регресс собственного фикса.** Фикс, меняющий компиляцию или поведение
  модуля (например замена `Найти()` на `Новый Соответствие(...)`), может
  сломать ранее зелёные сценарии. После такого фикса — перезапустить НЕ
  только целевой сценарий, но и ранее зелёные (регресс-прогон). В тикете 10
  фикс A2 через `Соответствие` (недоступен в режиме совместимости) уронил
  даже зелёный сценарий 1.
- **Режим совместимости.** Перед использованием конструктора/метода,
  доступность которого зависит от режима совместимости (`Новый Соответствие`,
  и т.п.), — проверить режим совместимости конфигурации и доки
  (`unica.documentation.search`). Альтернатива для поиска строк —
  `НайтиСтроки(<Структура>)`.
- **Порядок патч → загрузка.** Загрузка расширения (`operation: build`)
  берёт текущее состояние исходников. НЕ запускать загрузку параллельно с
  применением патча или до применения всех патчей одной логической правки:
  загрузка может взять промежуточную версию. Порядок: все патчи → затем
  одна загрузка.

## Грабли пересвёртывания контура (проверено 2026-09-03, после копии с прода)

- `"$V8R" extensions --name <Имя>` на **серверной** ИБ падает: «validation error:
  server-based IBCMD connection requires infobase.dbms.kind» — как снимать
  safe mode по типам ИБ и как он выглядит на прогоне, см. раздел
  «Безопасный режим расширений».
- `unica.runtime.execute` `operation: build` обрезается 30-с хостовым лимитом
  MCP (`Request timeout after 30000ms`, «outcome unknown»), **а загрузка
  продолжается** отдельным процессом v8-runner. Не повторять вызов и **не
  считать завершённой по исчезновению процесса**: признак завершения — строка
  `Build completed successfully` в `jobs/<id>/stdout.log` либо `finishedAt`
  в `unica.runtime.job.status` (опросить с `cwd` воркспейса). `pgrep` не видит
  джобу в фазе `queued`, а ранняя проверка на старой сборке даёт «прогон прошёл
  без моих правок».
- **Загрузка со устаревших исходников воскрешает удалённые объекты**, и обычной
  загрузкой их потом не убрать: в общей базе восстанавливаются элементы, которых
  в новых источниках уже нет, симптом — «Элемента формы с именем … не найдено»
  при корректном коде ветки. Лечение — полная пересборка расширения
  (`build --source-set <имя> --full-rebuild`), код не меняется. Отсюда порядок:
  все патчи → одна загрузка → регресс-прогон.
- **Бэкап несёт маркер хранилища конфигурации** (проверено 2026-09-09): после
  восстановления ИБ из бэкапа любая загрузка расширения падает с «Загрузка
  невозможна: текущая конфигурация помещена в хранилище». Пакетный ключ
  `/ConfigurationRepositoryUnbindCfg` БЕЗ живого соединения с хранилищем не
  помогает («Ошибка отключения от хранилища конфигурации»). Хранилище
  отключает оператор руками в конфигураторе; после этого загрузки идут штатно.

## Монитор прогонов: свой виртуальный дисплей и монитор оператора

**Дефолт — собственный виртуальный дисплей под каждый прогон.** Номер не
зашит: его выдаёт сам сервер (`Xvfb -displayfd`), поэтому два параллельных
агента получают разные дисплеи и не сбивают друг другу. Обёртки делают это
сами, руками Xvfb не поднимать:

```bash
P1C=.omp/plugins/node_modules/1c-omp
"$P1C/skills/unica-test-contour/scripts/test-yaxunit.sh"                     # свой дисплей
"$P1C/skills/unica-test-contour/scripts/xvfb-run-1c.sh" -- "$V8R" test va --no-build
# контрольный кадр через 75 с после старта клиента — вместо ожидания таймаута
"$P1C/skills/unica-test-contour/scripts/xvfb-run-1c.sh" --screenshot-at 75 \
    --screenshot-dir build/out/frames -- "$V8R" test va --no-build
# номер дисплея нужен для ручного скриншота:
"$P1C/skills/unica-test-contour/scripts/xvfb-run-1c.sh" --display-file build/out/display -- <команда>
DISPLAY=$(cat build/out/display) import -window root /tmp/frame.png
```

Что гарантирует обёртка: Xvfb живёт ровно столько, сколько команда (фоном из
одноразовой команды он умирает вместе с ней — симптом «Unable to initialize
GTK+ или connect to the windowing system» при, казалось бы, запущенном
`Xvfb`), дисплей снимается при любом выходе, **включая обрыв сессии (SIGHUP)**,
чужого дисплея не занят. При аварийном завершении гасится и само поддерево
прогона — тест-клиент не переживает раннер (иначе остаётся сирота,
который по стоп-протоколу приходится искать по PID). Утечки при жёстком
`kill -9` обёртки не ломают следующие прогоны: номер берётся свободный, а не
общий.

**Монитор оператора** — только по его явной команде, сессию не трогать.
Её дисплей определять по `$DISPLAY` живой сессии (это может быть `:1`, а не
`:0`), не хардкодить. Из контейнера нужен ещё и cookie:

```bash
DISPLAY=:1 XAUTHORITY=/run/user/1000/xauth_* "$V8R" test va --no-build
```

(`Invalid MIT-MAGIC-COOKIE-1 key` + `Unable to initialize GTK+` — симптом:
`XAUTHORITY` в контейнер не проброшен, имя файла — из живой сессии; на
собственном `-ac`-дисплее cookie не нужен.)

Случаи, когда прогон идёт **на мониторе оператора**, а не виртуально:

- **первая загрузка расширений тестового контура в чистую/восстановленную ИБ
  идёт БЕЗ проверки работы**: safe mode снимается только руками оператора в
  конфигураторе (см. «Безопасный режим» ниже), поэтому проверять прогон сразу
  после загрузки бессмысленно — загрузить, доложить, ждать снятия;
- **первый Vanessa-прогон в чистой ИБ** и **первый прогон после добавления
  новых Vanessa-тестов**: платформа поднимает модальный диалог доверия к
  внешнему EPF «Предупреждение безопасности» с дефолтной кнопкой «Нет» —
  на виртуальном мониторе его некому нажать;
- **первый прогон после обновления `vanessa-automation-single.epf`**: новая
  версия файла = новый источник доверия, диалог возвращается.

После однократного «Да» доверие запоминается (файл+пользователь), и дальнейшие
регресс-прогоны идут виртуально. **YAxUnit виртуален всегда, включая чистую
ИБ**: внешних EPF он не открывает и модальных диалогов не поднимает (проверено
2026-09-09: 34/34 на восстановленной базе). Единственное предусловие — снятый
safe mode: его диалог вешает клиент на любом мониторе (таймаут 300 с) и лечится
исключительно в конфигураторе, прожимкой не снимается.

**Оператора нет на месте** (ночной/автономный ран): прогон, требующий его
монитора, не запускать вовсе — поставить в очередь и доложить по возвращении,
не «докладывать и ждать» в цикле.

**Вылет по таймауту = стоп и доклад.** `enterprise test run timed out` (300 с) —
НЕ ретраить вслепую:

1. снять кадр дисплея этого прогона (`import -window root /tmp/frame.png` с
   `DISPLAY` из `--display-file`) — показать блокирующий диалог в докладе;
2. убить осиротевший `1cv8c` по конкретному PID (не по шаблону);
3. удалить `run.inprogress` в run-директории;
4. доложить оператору; дальнейшие прогоны — на его мониторе, пока причина
   не устранена.

## Слои тестирования

- YAxUnit — **только бэкенд**: модули, менеджеры, запросы, движения, расчёты.
  Поведение форм (открытие окна по кнопке, состав/типы реквизитов, UI-проверки)
  проверяется **только Vanessa**-сценарием в живом клиенте. `ПолучитьФорму` в
  серверном общем модуле недоступен (метод устаревший) — юнит-тест «форма
  резолвится по адресу» в принципе не пишем.

## Приёмка прогона (анти-«ложно-зелёный»)

Зелёный `summary: total=N, passed=N` ничего не гарантирует, а артефактов после
успешного прогона может не остаться вовсе:

- **Ложная приёмка.** Нескомпилировавшийся тестовый модуль НЕ роняет прогон:
  его тесты молча не регистрируются, summary зелёный. Единственный признак —
  строка `ЗагрузкаТестов: Ошибка инициализации модуля …`, и видна она только в
  **stdout раннера**: `enterprise.out.log` почти пуст (проверено 2026-09-21,
  когда 12-тестовый набор исчез именно так).
- **Артефакты удаляются.** Раннер держит отчёт в своём run-каталоге
  (`build/temp/yaxunit/runs/<id>/report.xml`) и удаляет этот каталог после
  успешного прогона — остаются только директории упавших (маркер
  `run.inprogress`). Путь отчёта не конфигурируется: у `tests.yaxunit` в схеме
  `v8project.yaml` только `timeouts`, ключа пути нет и в CLI.
- **`tools/yaxunit.json` раннер не читает** (проверено: в CLI `test yaxunit`
  только `all|module`, конфиг-файла нет; эксперимент — заведомо неверный
  `filter.extensions` не меняет `total`). На него не полагаться, фильтр — по
  имени расширения в самой YAxUnit/конфиге прогона.

Поэтому приёмка — не глазами по summary, а обёрткой, которая снимает доказательство
из JSON-конверта (`--json-message`) до того, как раннер его приберёт:

```bash
P1C=.omp/plugins/node_modules/1c-omp
"$P1C/skills/unica-test-contour/scripts/test-yaxunit.sh"
# приёмка пройдена = код 0; артефакты build/out/yaxunit/{last-run.json,junit.xml,log.txt,result.txt}
```

Обёртка выносит отказ при: ненулевом коде прогона, `failed`/`errors`,
непустом списке ошибок инициализации модулей и при `total=0` (0 зарегистрированных
тестов = несовпавший фильтр/имя расширения, а не «всё зелёное»).

Ручная проверка, если обёртка не используется: после КАЖДОГО прогона искать
`ЗагрузкаТестов: Ошибка инициализации модуля` в выводе раннера; junit-файл
раннер может удалить после парсинга — ориентир stdout.

**Vanessa** — приёмка по статусам шагов в `build/out/cucumber/CucumberJson.json`
(все `passed`). Строка `[error:test_report] Error:   0 (0%)` в выводе `test va` —
это парсинг строки статуса Vanessa («ошибок 0»), НЕ падение. JUnit-отчёт
Vanessa обычно не собирается: раннер перекрывает `КаталогВыгрузкиJUnit` и
каталог в run-каталоге остаётся пустым — на него не рассчитывать.

## Закрытие теста пропуском

`ЮТест.Пропустить(Сообщение)` — не «тихий выход», а исключение с префиксом
`[Skip]`, и статус от места вызова:

| Где вызван | Что получится |
|---|---|
| тело тестового метода | `Пропущен` (junit `skipped`) — назначение метода |
| обработчик события (`ПередКаждымТестом`, `ПередТестовымНабором`, …) | `ОшибкаОбработкиСобытия` → статус `Сломан`, **не** пропуск |
| вне прогона YAxUnit (шаг Vanessa, другой сеанс) | ошибка выполнения: контекста прогона нет |

Отсюда инварианты:

- **Причина пропуска живёт только в junit-отчёте прогона**: раннер печатает
  `SKIPPED <представление теста>` без текста причины, а run-директорию
  успешного прогона удаляет; `--json-message` причину не отдаёт. Поэтому причину
  **поймать фактом во время прогона** (обёртка копирует конверт) и вписать её
  текст в тикет — пересказывать по памяти нельзя.
- Причина называет **внешнюю** причину (нет данных, нет настройки, ограничение
  механизма), а не действия самого теста.
- Настройки, структуру и параметры объекта под тестом **не менять** ради
  достижимости утверждения: такая правка делает причину пропуска собственной
  выдумкой теста.
- Экспортную процедуру, которую вызывает Vanessa-шаг, пропуском закрывать
  нельзя — там остаётся `ВызватьИсключение` (проверить достижимость гварда
  заранее по шагам фич).
- Признак закрытого набора — `skipped=N` в summary **и** пойманный текст
  причины: `skipped` без причины приёмкой не считается.

## Установка расширений в ИБ (`.cfe`)

**Файловая ИБ** — `ibcmd` (учётка и пароль — в КОНЕЦ команды, пароль не печатать):

```bash
ibcmd infobase config load --db-path <путь к ИБ> --extension=<Имя> <файл.cfe> --user <user> --password <pass>
ibcmd extension update --db-path <путь к ИБ> --name=<Имя> --safe-mode=no --user <user> --password <pass>
ibcmd extension list --db-path <путь к ИБ> --user <user> --password <pass>     # приёмка
```

**Серверная (кластерная) ИБ** — `ibcmd` не работает (`--server` не распознаётся,
а на серверной ИБ `extensions --name` падает с «server-based IBCMD connection
requires infobase.dbms.kind»). Штатный путь — конфигуратор:

```bash
1cv8 DESIGNER /S "<сервер>\<база>" /N <user> /P <pass> \
  /LoadCfg <файл.cfe> -Extension <Имя> /UpdateDBCfg \
  /DisableStartupDialogs /DisableStartupMessages /Out build/<log>.log
```

- Ключ расширения — **`-Extension` с одним дефисом** (с двумя — «Ожидается файл
  конфигурации»); пустой пароль передавать **нельзя** (`/P""` → «Пользователь ИБ
  не идентифицирован»), в этом случае `/P` просто не передавать.
- **Тестовое расширение** — source-set в `v8project.yaml`, грузится как обычное:
  `unica.runtime.execute` `operation: build`, `sourceSet: "<тестовый source-set>"`
  (или `"$V8R" build --source-set <тестовый source-set>`).
- `load` .cfe НЕ подходит: probe требует, чтобы расширение уже существовало в ИБ.
- `ibcmd extension list` без учётки уходит в ожидание пароля и висит — в фон
  такой запуск не отправлять.

## Безопасный режим расширений

YAxUnit и тестовые расширения должны быть БЕЗ «Безопасного режима», иначе
«Расширение подключено в безопасном режиме. Чтение конфигурационного файла
недоступно» → JUnit report not produced (exit 3). На прогоне это выглядит не
как мгновенная ошибка, а как `enterprise test run timed out` (300 с): клиент
висит на модальном диалоге — сначала `enterprise.out.log`, а не «ИБ тормозит».

Снимается **по-разному**:

| ИБ | Как снять |
|---|---|
| файловая | инструментом: `ibcmd extension update --name=<Имя> --safe-mode=no …` |
| серверная | только руками оператора в конфигураторе — Unica/v8-runner на серверной ИБ этого не умеют |

После правки — F7 / `/UpdateDBCfg`. Время снятия: **до** первого прогона;
прогон до снятия не запускать.

## YAxUnit / Vanessa (общее)

- YAxUnit 25.x: модуль-регистратор `ИсполняемыеСценарии` + `ЮТТесты` (не префикс
  «Тест»). Имя расширения YAxUnit в ИБ — `YAXUNIT` (ключ `-Extension YAXUNIT`),
  проверить по списку расширений в `runner.log` прогона.
- **`tools/VAParams.json`** собирается скриптом из шаблона (см. `worktree-env`),
  ключи клиентов — ровно эти, другие имена Vanessa не распознаёт («Параметр не
  загружен»): `ПутьКИнфобазе`, `ПортЗапускаТестКлиента` (48000), `ДопПараметры`,
  `ТипКлиента` «Тонкий», `ИмяКомпьютера` localhost, `ТаймаутЗапуска1С ≥ 300`
  (25 с не доживает до холодного старта: «Не получилось подключить TestClient,
  PID=0»).
- **Команду запуска тест-клиента собирает Vanessa, и `ДопПараметры` на этом пути
  не используется**: `/N"пользователь"` добавляется всегда, `/P"пароль"` —
  только если пароль передан **параметром шага**. Поэтому для сценариев, самих
  подключающих клиент (`я подключаю TestClient "…" логин "…" пароль "…"`), пароль
  берётся из локального `tools/va-env.local.json` и подставляется в шаг кодом
  (шаблон — в навыке `unica-test-contour`); сам текст пароля в `.feature` не
  попадает. Иначе клиент стартует без пароля и висит до таймаута
  (`enterprise exit code 139`, junit не формируется).
- Раннер **перекрывает** при прогоне `WorkspaceRoot`, `КаталогФич`,
  `СписокФичДляВыполнения`, `КаталогВыгрузкиJUnit`, путь лога и файла статуса —
  держать их в файле не нужно.
- Первый запуск клиента на **свежей** файловой ИБ поднимает модальный диалог
  «Региональные настройки»: его нужно прожимать на дисплее прогона, иначе
  тест-клиент висит. Один раз, дальше база стартует без него.

- Учётка ИБ — в `v8project.local.yaml` (не читать значения; скрипт-обёртка).
