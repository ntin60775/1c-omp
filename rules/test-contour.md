# Тестовый контур 1С: рабочие команды и грабли


## Прогон тестов: только встроенный раннер Unica

Единственный раннер — **v8-runner, встроенный в Unica** (в Unica 0.12.3 — v8-runner 0.5.1).
Путь версионирован — резолвить динамически, не хардкодить:

    V8R=$(ls -d ~/.codex/unica/runtimes/*/linux-x64/bin/linux-x64/v8-runner 2>/dev/null | sort -V | tail -1)

Контрактный gap (проверено 2026-08-28): `unica.runtime.execute operation: test`
НЕ экспонирует флаг `--no-build` и всегда пересобирает ВСЕ source-set'ы, включая
основную конфигурацию, — десятки минут, неприемлемо. Расширения пересобирать
полной загрузкой можно; основную конфигурацию — нельзя.

Штатный цикл (одинаков для YAxUnit и Vanessa):

1. Загрузка изменений — через MCP, по source-set'у:
   `unica.runtime.execute` `operation: build`, `sourceSet: "<имя source-set'а>"`
   (каждое изменённое расширение отдельно, включая тестовое). Полная загрузка
   расширения ~2–3 мин.
2. Прогон — прямой запуск встроенного раннера с `--no-build` (обход MCP-контракта,
   флаг там отсутствует):
   ```bash
   "$V8R" test yaxunit all --no-build    # YAxUnit (все тесты)
   "$V8R" test va --no-build             # Vanessa (профиль из v8project.yaml)
   ```
   Запуск из корня worktree/проекта.

Легитимность обхода: правила проекта имеют приоритет над инструкциями skill'а
Unica («Do not start internal runner… directly»); обход допустим как единственный
путь к `--no-build` и/или по явной команде оператора. Перед обходом называть
отсутствующую возможность контракта.

builder: **DESIGNER** (подключение через кластер 1С; IBCMD требует прямого доступа
к СУБД `infobase.dbms` — не используется).

## Грабли прогона (проверено 2026-08-28, дополнено 2026-09-01)

- `--feature` у `"$V8R" test va` матчится **относительно `КаталогФич`**: передавать
  только имя файла (`"ИмяФичи.feature"`), а не путь `"features/ИмяФичи.feature"`.
  Иначе — «Сценарии для выполнения не обнаружены», пустой junit, exit с
  `junit file is empty` при живой ИБ и корректных тегах.
- `unica.runtime.job.wait` обрезается хостовым 30-с лимитом MCP — не полагаться
  на него: опрашивать `unica.runtime.job.status` (обязательно с `cwd` воркспейса,
  иначе «record is missing») или ждать паузой вне MCP.
- `unica.runtime.job.start` `operation: build` при провале partial load
  **сам ретраит одной полной пересборкой** (`--full-rebuild`); итог — exit 0,
  в warnings: «reported a completed partial load failure; Unica retried once».
  Повторный manual full-rebuild не нужен.
- Partial load расширения падает с «Исключение XDTO произошло при чтении
  файла- …Form.xml», когда в partial-списке есть **формы** (проверено
  2026-09-01: падает на любой версии формы, full load той же версии проходит).
  Модули (.bsl) грузятся partial-ом нормально. Если менялись формы — грузить
  full load: MCP `unica.runtime.execute build` по source-set'у или
  `"$V8R" build --source-set <имя> --full-rebuild`. Основную конфигурацию
  по-прежнему не пересобирать.

## Регресс собственного фикса и порядок операций (факапы A3, D1 тикета 10)

- **Регресс собственного фикса.** Фикс, меняющий компиляцию или поведение
  модуля (например замена `Найти()` на `Новый Соответствие(...)`), может
  сломать ранее зелёные сценарии. После такого фикса — перезапустить НЕ
  только целевой сценарий, но и ранее зелёные (регресс-прогон). В тикете 10
  фикс A2 через `Соответствие` (недоступен в режиме совместимости) уронил
  даже зелёный сценарий 1.
- **Режим совместимости.** Перед использованием конструктора/метода,
  доступность которого зависит от режима совместимости (`Новый Соответствие`,
  и т.п.), — проверить режим совместимости конфигурации и доки
  (`unica.documentation.search`). Альтернатива для поиска строк —
  `НайтиСтроки(<Структура>)`.
- **Порядок патч → загрузка.** Загрузка расширения (`operation: build`)
  берёт текущее состояние исходников. НЕ запускать загрузку параллельно с
  применением патча или до применения всех патчей одной логической правки:
  загрузка может взять промежуточную версию. Порядок: все патчи → затем
  одна загрузка.

## Грабли пересвёртывания контура (проверено 2026-09-03, после копии с прода)

- `"$V8R" extensions --name <Имя>` на **серверной** ИБ падает: «validation error:
  server-based IBCMD connection requires infobase.dbms.kind». Safe mode у
  расширений на серверной ИБ снимается **только руками в конфигураторе**
  (оператор) — операция Unica тут недоступна.
- Symptom включённого safe mode на прогоне — не мгновенная ошибка, а
  **`enterprise test run timed out` (300 с)**: тест-клиент висит на модальном
  «Расширение подключено в безопасном режиме. Чтение конфигурационного файла
  недоступно». Таймаут прогона = сначала смотреть `enterprise.out.log`, а не
  «ИБ тормозит».
- `unica.runtime.execute` `operation: build` обрезается 30-с хостовым лимитом
  MCP (`Request timeout after 30000ms`, «outcome unknown»), **а загрузка
  продолжается** отдельным процессом v8-runner. Не повторять вызов: ждать
  окончания `pgrep -f 'v8-runner.*build --source-set'`.
- Имя расширения YAxUnit в ИБ — **`YAXUNIT`** (ключ `-Extension YAXUNIT`);
  проверить после установки по списку расширений в `runner.log` прогона.
- `[error:test_report] Error:   0 (0%)` в выводе `test va` — парсинг строки
  статуса Vanessa («ошибок 0»), НЕ падение. Истинная приёмка BDD — статусы
  шагов в `build/out/cucumber/CucumberJson.json` (все `passed`).
- **Бэкап несёт маркер хранилища конфигурации** (проверено 2026-09-09): после
  восстановления ИБ из бэкапа любая загрузка расширения падает с «Загрузка
  невозможна: текущая конфигурация помещена в хранилище». Пакетный ключ
  `/ConfigurationRepositoryUnbindCfg` БЕЗ живого соединения с хранилищем не
  помогает («Ошибка отключения от хранилища конфигурации»). Хранилище
  отключает оператор руками в конфигураторе; после этого загрузки идут штатно.

## Монитор прогонов: виртуальный `:99` и монитор оператора (проверено 2026-09-09)

- **Дефолт — виртуальный монитор**: `Xvfb :99 -screen 0 1920x1080x24 -ac`,
  запуск `"$V8R" test …` с `DISPLAY=:99` (distrobox пробрасывает X-сокет).
  Сессию оператора не трогать без его явной команды; её дисплей определять по
  `$DISPLAY` живой сессии (это может быть `:1`, а не `:0`), не хардкодить.
  Xvfb поднимать перед прогоном и останавливать после (не оставлять висеть);
  если `:99` занят — проверить `pgrep Xvfb` и взять свободный номер.
- **Первая загрузка расширений тестового контура в чистую/восстановленную ИБ
  идёт БЕЗ проверки работы**: safe mode снимается только руками оператора в
  конфигураторе (Unica/v8-runner на серверной ИБ этого не умеют), поэтому
  проверять прогон сразу после загрузки бессмысленно — загрузить, доложить,
  ждать снятия safe mode.
- **Первый Vanessa-прогон в чистой ИБ — на мониторе оператора** (`DISPLAY`
  его сессии, только по его явной команде): платформа поднимает модальный
  диалог доверия к внешнему EPF «Предупреждение безопасности» с дефолтной
  кнопкой «Нет» — на виртуальном мониторе его некому нажать.
- **После добавления новых Vanessa-тестов первый прогон — всегда на мониторе
  оператора**, пока ошибки не кончатся; зелёный прогон там же разрешает
  дальнейшие регресс-прогоны этого набора на `:99`.
- **YAxUnit — всегда на `:99`, включая чистую ИБ**: внешних EPF он не
  открывает, модальных диалогов в прогоне нет (проверено 2026-09-09: 34/34
  на восстановленной базе). Единственное предусловие — снятый safe mode:
  его диалог на любом мониторе только вешает клиент (таймаут 300 с),
  лечится исключительно в конфигураторе, прожимкой не снимается.
- **Ранняя проверка вместо ожидания таймаута**: при прогоне на `:99` через
  60–90 с после старта клиента сделать контрольный кадр
  (`DISPLAY=:99 import -window root /tmp/x99-check.png`); если на нём
  модальный диалог — не ждать 300-секундного таймаута, сразу стоп-протокол.
- **Вылет по таймауту на виртуальном мониторе = стоп и доклад.**
  `enterprise test run timed out` (300 с) на `:99` — НЕ ретраить вслепую:
  1. снять кадр дисплея: `DISPLAY=:99 import -window root /tmp/x99.png` —
     идентифицировать блокирующий диалог (докладывать с этой уликой);
  2. убить осиротевший `1cv8c` по конкретному PID (не по шаблону),
  3. удалить `run.inprogress` в run-директории,
  4. доложить оператору; дальнейшие прогоны — на его мониторе, пока причина
     не устранена.
- **Оператора нет на месте** (ночной/автономный ран): прогон, требующий его
  монитора (чистая ИБ, новые Vanessa-тесты, обновлённый EPF), не запускать
  вовсе — поставить в очередь и доложить по возвращении; не «докладывать и
  ждать» в цикле.
- Диалог доверия к EPF: после однократного «Да» от оператора доверие
  запоминается (файл+пользователь) и следующие прогоны идут на `:99` без
  диалога; но он **возвращается после обновления
  `vanessa-automation-single.epf`** (новая версия файла = новый источник) —
  первый прогон после обновления VA снова на мониторе оператора.

## Слои тестирования и ложно-зелёный YAxUnit

- YAxUnit — **только бэкенд**: модули, менеджеры, запросы, движения, расчёты.
  Поведение форм (открытие окна по кнопке, состав/типы реквизитов, UI-проверки)
  проверяется **только Vanessa**-сценарием в живом клиенте. `ПолучитьФорму` в
  серверном общем модуле недоступен (метод устаревший) — юнит-тест «форма
  резолвится по адресу» в принципе не пишем.
- **Ложная приёмка**: нескомпилировавшийся тестовый модуль НЕ роняет прогон —
  его тесты молча не регистрируются, summary остаётся зелёным
  (`total=N, passed=N`). Единственный признак — `[error:test_report] …
  ЗагрузкаТестов: Ошибка инициализации модуля …` в выводе раннера. После каждого
  прогона проверять эту строку, а не только summary; junit-файл раннер может
  удалять после парсинга — ориентироваться на вывод.

## Установка расширений в серверную ИБ

- **`.cfe` артефакты** (YAxUnit): `ibcmd` НЕ работает с кластерными ИБ
  (`--server` не распознаётся). Штатный путь — конфигуратор:
  ```bash
  1cv8 DESIGNER /S "<сервер>\<база>" /N <user> /P <pass> \
    /LoadCfg <файл.cfe> -Extension <Имя> /UpdateDBCfg \
    /DisableStartupDialogs /DisableStartupMessages /Out build/<log>.log
  ```
  Ключ расширения — **`-Extension` с одним дефисом** (с двумя — «Ожидается файл конфигурации»).
  Учётку брать из `v8project.local.yaml` (скрипт-обёртка, пароль не печатать).
- **Тестовое расширение** — source-set в `v8project.yaml`, грузится так же:
  `unica.runtime.execute` `operation: build`, `sourceSet: "<тестовый source-set>"`
  (или `"$V8R" build --source-set <тестовый source-set>`).
- `load` .cfe НЕ подходит: probe требует, чтобы расширение уже
  существовало в ИБ.

## YAxUnit / Vanessa (общее)

- YAxUnit 25.x: модуль-регистратор `ИсполняемыеСценарии` + `ЮТТесты` (не префикс «Тест»).
- **Safe-mode**: YAxUnit и тестовые расширения должны быть БЕЗ «Безопасного режима» в
  конфигураторе, иначе: «Расширение подключено в безопасном режиме. Чтение
  конфигурационного файла недоступно» → JUnit report not produced (exit 3).
  После правки — F7 (обновить БД).
- Vanessa: `tools/VAParams.json` → `ДанныеКлиентовТестирования`: `ПутьКИнфобазе`
  (`Srvr="<сервер>";Ref="<база>";`), `ПортЗапускаТестКлиента` (48000), `ДопПараметры`
  (`/N"<пользователь>" /P"<пароль>"` — пароль локально, не коммитить), `ТипКлиента`
  «Тонкий», `ИмяКомпьютера` localhost; `ТаймаутЗапуска1С ≥ 300`.

## Аутентификация и блокировки

- Учётка ИБ — в `v8project.local.yaml` (не читать значения; скрипт-обёртка).
- Конфигуратор держит монопольную блокировку ИБ: не запускать сборку/load при
  открытом конфигураторе; зависшие `1cv8 DESIGNER` — проверять `ps aux | grep 1cv8`.
