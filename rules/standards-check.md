# Гарантированная проверка кода по стандартам через Unica

Каждая правка BSL-кода сопровождается **обязательным прогоном по
стандартам через Unica**. Это постоянный шаг цикла, а не опция и не
реакция на конкретное нарушение. Агент не проверяет стандарты «по памяти»
и не решает сам, подпадает ли код под стандарты, — он прогоняет код через
анализатор и читает результат.

## Механизм (инструменты Unica)

### 1. Прогон кода по source-set'у — `unica.code.diagnostics`

После любой правки кода в source-set'е — прогнать анализатор:

```
unica.code.diagnostics {
  "action": "analyze",
  "sourceSet": "<имя source-set'а>",
  "cwd": "<корень проекта>"
}
```

Возвращает findings провайдера `bsl-analyzer` с кодами и severity.
Для конкретного объекта:

```
unica.code.diagnostics {
  "action": "findings",
  "sourceSet": "<имя>",
  "metadataPath": "<адрес объекта>",
  "cwd": "<корень>"
}
```

### 2. Объяснение находок и фрагментов — `unica.standards.explain`

Для каждой находки или спорного фрагмента — получить стандарт:

```
# по коду диагностики
unica.standards.explain { "codes": ["АПК:8"], "cwd": "<корень>" }

# по фрагменту BSL
unica.standards.explain { "snippet": "<фрагмент кода>", "cwd": "<корень>" }

# по номеру/алиасу стандарта
unica.standards.explain { "idOrAliasOrUrl": "474", "cwd": "<корень>" }
```

### 3. Поиск стандарта — `unica.standards.search`

Когда нужно найти правило по фразе или коду:

```
unica.standards.search { "query": "<фраза или код>", "cwd": "<корень>" }
```

## Правило

1. После ЛЮБОЙ правки BSL-кода — `unica.code.diagnostics` (`analyze` по
   source-set'у или `findings` по объекту). Пропуск = нарушение цикла.
2. Каждую находку с severity `error`/`warning` — разобрать через
   `unica.standards.explain` и устранить либо осознанно обосновать.
3. До записи спорного кода — проверить фрагмент через
   `unica.standards.explain` (`snippet`), не дожидаясь падения прогона.
4. Не решать «по памяти», подпадает ли код под стандарты: анализатор
   решает, агент читает результат.

## Разрешение конфликтов: находка против правил проекта

Находки анализатора **неоднородны** — они мешают проверки корректности и
проверки стиля. Конфликт с проектными правилами возможен только на
стилевой части. Иерархия:

| Тип находки | Разрешение |
|---|---|
| **Корректность/поведение** (несуществующий метод, недоступный конструктор, сломанный API, security) | **Исправляется всегда.** Никакой проектный стиль не перекрывает реальный баг — это не «стиль» |
| **Стилевая находка, конфликтующая с явным проектным правилом** | **Проектное правило побеждает.** Оставить по-проектному, НЕ «исправлять» под стандарт |
| **Стилевая находка без проектного перекрытия** | Исправляется |

Проект уже декларирует этот принцип в `rule://1c-bsl-code-style`:
- «все многострочные конструкции закрываются скобкой на отдельной строке…
  **даже если статанализ ругается на такой стиль — это правило имеет
  высший приоритет**»;
- «табы на пустых строках внутри методов — не trailing whitespace, не
  удалять»;
- «при конфликте по локальной форме приоритет у этого правила».

**Предохранитель:** перекрыть стилевую находку можно, только сославшись
на **конкретное** проектное правило (файл + пункт). Находку
корректности/поведения нельзя перекрыть ничем. «Проектный стиль» — не
оправдание игнорировать баг.

## Пример того, что ловит прогон (не исчерпывающий)

Буква «ё» запрещена в именах/синонимах/комментариях/текстах модулей —
это лишь один класс находок:

| Диагностика | Что ловит | Стандарт |
|---|---|---|
| АПК:8 / АПК:7 / АПК:6 | «ё» в имени / синониме / комментарии | std467, std474 |
| BSLLS:YoLetterUsage | «ё» в текстах модулей | std456 |
| v8cs:mdo-ru-name-unallowed-letter | «ё» в метаданных | std474 |

Тот же прогон ловит модальные окна, `Перейти`, глобальные переменные,
длину методов, локализацию и сотни других диагностик. Суть правила —
**прогон всегда**, а не реакция на «ё».

## Детерминированный слой

`unica.code.diagnostics`, `unica.standards.search`, `unica.standards.explain`
засчитываются хуком `doc-gate.ts` как сверка (разблокируют последующие
мутации). Прогон по стандартам таким образом встроен в обязательный цикл
«сверка → мутация».

## MUST

- Прогонять `unica.code.diagnostics` после каждой правки кода.
- Разбирать каждую находку `error`/`warning` через `standards.explain`.
- Находки корректности/поведения исправлять всегда.
- Стилевую находку, перекрываемую проектным правилом, — оставлять
  по-проектному и ссылаться на конкретное правило (файл + пункт).

## MUST NOT

- Пропускать прогон по стандартам после правки кода.
- Решать по памяти, нарушает ли код стандарты.
- «Исправлять» стилевую находку под стандарт, если она перекрыта явным
  проектным правилом.
- Перекрывать находку корректности/поведения ссылкой на «проектный стиль».
- Игнорировать находки анализатора без осознанного обоснования.
