# Стек инструментов платформы (2026-07-28, обновлено 2026-08-28)

Unica MCP — ОБЯЗАТЕЛЬНА при любой работе с 1С (сборка, загрузка, выгрузка,
метаданные, тесты): `mcp__unica__*`. Приоритет: Unica → прямое редактирование
XML → CLI встроенного в Unica `v8-runner` через bash (понижение уровня —
только с явным называнием причины).

## MUST NOT: прямое редактирование исходников 1С

Файлы в `src/cf/`, `src/cfe/`, `src/epf/`, `src/erf/`, `tests/cfe/`,
`tests/epf/` — **запрещено** редактировать инструментами `edit`, `write`,
`sed -i`, перенаправлениями и любыми другими способами прямой записи.
Хук `unica-gate.ts` блокирует такие вызовы детерминированно.

Единственный путь изменения — соответствующий инструмент Unica MCP
(маршрутизация: `rule://unica-source-gate`). Чтение (`read`, `grep`,
`glob`, `unica.source.read`) — без ограничений.

Основные операции Unica — через `unica.runtime.execute` (`operation`:
build/dump/make/load/syntax/test/launch; `cwd` — корень проекта; мутации —
только с `dryRun: false` по явному запросу пользователя). Длительные
операции — `unica.runtime.job.*` (start/status/wait/logs/cancel). Точечная
работа с метаданными — `unica.cf.*`, `unica.cfe.*`, `unica.form.*`,
`unica.meta.*`, `unica.dcs.*`, `unica.mxl.*`, `unica.role.*`,
`unica.interface.*`, `unica.subsystem.*`, `unica.template.*`; код —
`unica.code.*` (search/grep/patch/diagnostics/outline/definition/graph);
стандарты — `unica.standards.*` (search/explain).

Проверенные требования контура:
- платформа регистрируется для v8find деревом симлинков
  `/opt/1cv8/x86_64/<версия>/1cv8*` → `tools/platform/bin/*` (нужен pkexec);
- `tools/yaxunit.json` — НЕ конфиг прогона: раннер его не читает (см.
  `test-contour`, раздел «Приёмка»), конфиг прогона — `v8project.yaml` и сама
  YAxUnit;
- на тестируемой ИБ не должен быть открыт Конфигуратор — загрузка/дампы требуют
  монопольной блокировки (все исключения и кто держит базу — `ib-contour`).

## Долгие операции и 30-с лимит MCP

Хост обрывает любой `tools/call` примерно на 30-й секунде; процесс при этом
**не убивается** и продолжает работать. Синхронный `unica.runtime.execute` на
длинных операциях (полная сборка, дамп) поэтому врёт про исход. Долгое — только
через `unica.runtime.job.start` (start/status/logs/cancel), `job.wait` тоже
обрывается, так что наблюдать — `job.status` с `cwd` воркспейса. Как отличить
завершение от висящего — `test-contour`, «Грабли прогона».

Если Unica в данной операции не даёт нужной возможности (например полной
выгрузки — `job.start` отвечает отказом), это называется вслух перед обходом,
и обход идёт прямым запуском встроенного раннера; названные обходы — в
`unica-mcp` и `ib-contour`.

## Понижение уровня: куда уходят fallback'ы

Приоритет `Unica → прямое редактирование XML → shell/платформа` — общий.
Проект может вставить между Unica и прямой правкой свой MCP-сервер платформы
(например расширение IDE): это допустимо, если его состояние проверено фактом
(рукопожатие, список инструментов, долгие операции с выключенным ожиданием —
иначе IPC-обработчик блокируется и ответа нет) и если его порт/адрес
перепроверяются перед использованием: IPC-порты привязаны к сеансу IDE и
меняются при его перезапуске, а устаревшая запись в `.omp/mcp.json` роняет
подключение. О таком вставном fallback'е сообщать явно — он не является
частью стека плагина.

НЕ верифицировано (до проверки — не утверждать):
- применяет ли `unica.runtime.execute` (build/load) изменения к конфигурации
  БД автоматически. До проверки считать UpdateDBCfg отдельным шагом; если в
  проекте есть правило `DB_UPDATE_AND_LAUNCH` (агент только загружает, применяет
  и запускает клиент пользователь) — следовать ему.
