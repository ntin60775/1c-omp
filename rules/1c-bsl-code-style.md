# Стиль 1С BSL-кода

Правило задаёт локальную форму кода: шапку модуля, дробление методов,
промежуточные переменные, doc-comments, форматирование. Это не review по
`v8std` (для него — `$1c-bsl-review-standards`); при конфликте по локальной
форме (форматирование, декомпозиция, doc-comments) приоритет у этого
правила. Смежные границы: `$1c-bsl-architecture-ddd` — архитектурная
декомпозиция, `$1c-bsl-bsp-patterns` — штатные методы БСП.

База правила: `.omp/rules/1c-bsl-code-style/` (далее — `<base>`).
Каждое правило имеет один канонический дом; примеры «менее удачно → лучше»
живут в том же файле.

## Роутинг: что читать

Читать только файлы, применимые к scope. Консультация без реального кода:
только `principles.md` + `anti-overengineering.md`.

| Scope | Файл в `<base>/references/` |
|---|---|
| любая правка (обязательно) | `behavior-change-guard.md` |
| целый модуль: сначала шапка и верхний уровень, потом методы | `module-header.md` |
| whitespace, табы, регистр `Не`/`И`/`Или` | `bsl-formatting.md` |
| именование | `naming.md` |
| декомпозиция, промежуточные значения, конструкторы, ветвление | `method-composition.md` |
| компактная/многострочная форма вызовов | `call-layout.md` |
| doc-blocks и их уместность | `doc-comments.md` |
| legacy/внешние границы, явные преобразования, глобальное состояние | `review-feedback.md` |
| ядро style-эвристик | `principles.md` |
| перегруз кода абстракциями | `anti-overengineering.md` |

Профили в `<base>/profiles/` — только при подтверждённой применимости, это
не универсальные нормы: `query-texts.md` — `Запрос.Текст` через helper-ы и
область `ТекстыЗапросов`; `orchestration.md` — orchestration-модули.

## Процедура работы с реальным кодом

1. Inventory scope: целый модуль / whitespace-правки / `Запрос.Текст` /
   orchestration / граница legacy или внешнего контракта / затронутые
   методы / право на запись.
2. Прочитать применимые файлы по таблице роутинга.
3. Прогнать guard: `python3 <base>/scripts/bsl_style_check.py <path>`
   (при праве на запись — с `--fix`).
4. Проверить семантику вне guard-а: naming, декомпозиция, overengineering,
   уместность doc-comments, профили.
5. Локальные детерминированные findings исправлять самостоятельно при праве
   на запись; спрашивать только о спорных, неоднозначных или тяжёлых по
   последствиям решениях.
6. После правок — guard повторно + сверка diff с
   `references/behavior-change-guard.md`: только intended изменения.
7. В финальный ответ: что исправлено автоматически, что осталось residual
   findings или рисками, ограничения проверки.

Не завершать работу сырым списком исправимых findings, если их можно
безопасно закрыть самостоятельно.

## Машинный guard

`<base>/scripts/bsl_style_check.py` закрывает детерминированные правила:

- `tab-rhythm` — пустые строки внутри методов держат tab-уровень блока (fix);
- `operator-case` — операторы только `Не`, `И`, `Или` (fix);
- `empty-ctor-parens` — пустой конструктор без скобок (fix);
- `comma-space` — пробел после запятой в списке аргументов (fix);
- `struct-ctor-args` — `Новый Структура` не более чем с одним значением;
- `if-nesting` — вложенность `Если...Тогда` не глубже двух уровней;
- `return-expression` — прямой `Возврат Выражение;`;
- `query-text-format` — query text literal: `= "` + `|` строки + `|";`;
- `query-istina` — WHERE с 2+ условиями: первое условие `ИСТИНА`;
- `boolean-column` — булево присваивание: `(Ложь Или ...)` / `(Истина И ...)`;
- `ternary-long` — тернарный >140 символов в одну строку;
- `call-args-multi` — вызов с 3+ аргументами в одну строку;
- `chained-call` — цепочка `)...Метод(` / вызов объекта аргументом вызова;
- `nested-call-arg` — вызов или конструктор аргументом другого вызова —
  вынести аргумент в именованную переменную;
- `omitted-arg` — пропущенный аргумент `Метод(, Текст)`;
- `named-type-desc` — повтор `Новый ОписаниеТипов(...)` в методе inline.

Прогонять при любой BSL-правке и после auto-fix повторно. Guard не закрывает
семантику (naming, декомпозиция, doc-comments, поведение) — она на агенте.
Новые детерминированные правила развивать через guard-скрипт, а не прозой;
check-id синхронизировать с `references/`.

## MUST

- для целого модуля сначала проверять шапку и верхний уровень файла, потом
  методы;
- при любой BSL-правке прогонять guard, после fix — повторно;
- исправлять локальные детерминированные findings при праве на запись;
- каждый edit-pass сверять с `references/behavior-change-guard.md`;
- профили применять только при подтверждённой применимости.

## MUST NOT

- менять поведение под видом стиля: защитные условия, порядок
  fallback-веток, момент создания объекта, источник даты, вызываемый API;
- удалять табы на пустых строках внутри методов как trailing whitespace;
- запускать массовое переформатирование модуля, если задача не была именно
  форматированием;
- создавать вложенность `Если...Тогда` глубже двух уровней;
- восстанавливать doc-comments ради шаблона;
- подменять style-review формальным standards-review;
- принимать унаследованную локальную форму за норму, если она расходится с
  правилами и не требуется внешним контрактом.
